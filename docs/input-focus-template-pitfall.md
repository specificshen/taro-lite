# 输入组件 focus 模板机制坑位记录

> 记录 Skyline/glass-easel 下 input/textarea 的 focus 绑定机制踩坑与最终决策。
> 结论先行：**input/textarea 的 focus 保持 webview 时代的双模板机制，不得改为单模板响应式绑定**（v2.0.0-alpha.4，提交 7a0ea97）。

## 现象（2.0.0-alpha.1 ~ alpha.3 可复现）

- 弹窗表单中输入时**点选下拉选项**（兄弟节点卸载）→ scroll-view 异常滚动 + 键盘自动收起（签约弹窗选中签约公司）
- 受控 Input **删空内容**（清除按钮/计数器等兄弟节点卸载）→ 键盘自动收起
- 键盘顶输入卡片（KeyboardComposer）单行模式**回填文本摇晃**（此前误诊为排版时序问题并做多轮样式/动画对策，回退双模板后症状消失，实为本坑同源）
- 日常逐字输入正常（`c0d22c5` 修复后仅剩上述场景）

同一业务代码在 1.2.8 底座上全部正常，确证为底座回退。

## 根因

`496e2e7` 将 input/textarea 的 focus 从「focus/blur 双模板」改为「单模板响应式绑定」（`focus="{{i.focus||undefined}}"`），意图是让 focus 属性可用、避免切换时重建节点。

但 Taro 模板渲染存在 **cn 重排机制**：兄弟节点增删时，父节点的子节点数组整体重发，数组中每个节点的**全部绑定属性重新求值并推给原生组件**。单模板下 focus 绑定常驻模板，聚焦中的原生输入组件因此反复收到 focus 相关的绑定求值结果，被打扰后强制失焦收键盘（并可能伴随节点状态重置引发的滚动）。

`c0d22c5` 曾将 focus 默认值从恒 false 改为 undefined 透传（求值 undefined 时不下发），只盖住了日常逐字输入场景；在点选回填、兄弟卸载等 cn 重排场景下，glass-easel 对「有绑定但求值 undefined」的处理并不等价于「无绑定」，问题依旧。

## 决策：回退双模板

- 双模板稳态（未传 focus / focus=false）渲染**无 focus 绑定**的分支，节点数据完全不携带 focus，从根上免疫 cn 重排打扰。
- 代价（与 1.2.8 相同的既有取舍）：focus prop **动态切换**会换模板、销毁重建原生节点，光标与内部滚动状态丢失。
- 编辑器（editor）组件本就保留双模板，不受影响。

## 使用约束（业务侧）

- **不要**用 focus 状态切换控制已挂载输入框的聚焦/失焦；收起键盘用 `Taro.hideKeyboard()`。
- 需要打开即聚焦的场景，用**挂载时 `focus={true}`**（新建节点直接带焦点，无切换问题）。KeyboardComposer 即此模式，不受双模板影响。
- 复杂输入场景（下拉自动补全、长表单、弹窗内输入）**优先 keyboard-composer 形态**：页面字段只做展示，点击唤起键盘顶输入卡片，页面内不留原生输入组件，彻底绕开键盘避让/cn 重排/受控回环一整类问题。

## 同源次生坑：受控 value 等值跳过（2.0.0-alpha.1 ~ alpha.4 可复现）

`e489e60` 为减少受控回环的冗余 setData，给 FormElement 加了 lastNativeValue 跟踪：React 回写值与原生已显示值相等时跳过下发。

**症状**：签约公司 AutocompleteInput 场景，输入一个字后输入框被**旧值整体回填**（如输入"阿"瞬间变回"阿里巴巴（中国）…"）。

**根因**：与 cn 重排同源。输入触发下拉过滤 → 兄弟节点增删 → cn 重排把节点数组（含 input 的 value 绑定快照）整体重发，重发值可能是渲染批次的旧值。1.2.8 时代每次 INPUT 事件都会**主动真实下发当前键入值**，恰好充当纠错者把重发的旧值覆盖掉；等值跳过把这个纠错通道关了，旧值下发后无人纠正，回填定格。

**决策**：回退 `e489e60`（v2.0.0-alpha.5），恢复 1.2.8 行为——INPUT 事件一律真实下发 setData，受控回写不做等值跳过。冗余下发的性能代价可忽略，正确性优先。回归约束固化在 `packages/taro/tests/runtime/form.spec.ts`。
